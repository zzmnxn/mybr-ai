기존에는 [티스토리](https://wlals916.tistory.com/)에 개발 글을 작성했다.
글을 쓰는 것 자체는 어렵지 않았지만, 글이 하나둘 쌓이면서 아쉬운 점이 생겼다. 글마다 내용과 말투가 조금씩 달랐고, 새로운 내용을 공부할 때 기존에 작성한 글을 찾아 다시 정리하는 일도 번거로웠다.
무엇보다 **내가 공부한 개념과 실제로 겪은 문제들이 서로 연결되어 있지 않다는 점**이 가장 아쉬웠다.
하나의 프로젝트에서 새로운 기술을 공부하고, 그 기술을 적용하다가 오류를 만나고, 해결하는 과정에서 또 다른 개념을 배우기도 한다. 실제 개발 경험은 이렇게 이어지는데, 블로그에서는 각각의 글이 독립적으로 남아 있었다.
태그나 카테고리로 분류할 수는 있었지만, 내가 원했던 건 단순한 분류보다 조금 더 유기적인 연결이었다.

마침 개발할 때 참고하기 위해 Obsidian 안에 [LLM Wiki](../../topics/plan-devwiki)를 구축하고 있었다. 공부한 개념과 프로젝트 경험을 정리하면서, AI를 이용해 문서를 관리하고 연결하는 방법도 고민하던 중이었다.
그러다 문득 이런 생각이 들었다.

> **블로그도 Wiki처럼 만들면 어떨까?**

하나의 글에서 관련 개념으로 이동하고, 그 개념을 활용했던 다른 프로젝트나 문제 해결 기록까지 따라갈 수 있다면 훨씬 활용도가 높을 것 같았다.
최근에는 AI 코딩 도구를 활용해 개발할 수 있는 범위도 넓어졌다. 예전이었다면 개인 블로그를 직접 구축하는 데 부담을 느꼈겠지만, 이번에는 AI를 활용하는 개발 방식 자체도 실험해 보고 싶었다.
그렇게 mybr.ai를 만들기 시작했다.

## 글을 쌓는 대신 지식을 연결한다면

기존 블로그에서는 Backend, Frontend 같은 카테고리를 중심으로 글을 분류했다. 하지만 실제 개발 과정에서는 하나의 경험이 특정 카테고리에만 속하지 않는 경우가 많았다.

예를 들어 React 애플리케이션을 개발하다 문제가 발생했다고 해 보자. 문제를 해결하는 과정에서 React의 상태 관리나 렌더링 원리를 새롭게 이해할 수도 있고, 원인을 따라가다 보면 API 통신이나 백엔드의 데이터 처리 방식까지 살펴보게 될 수도 있다.

이때 문제를 해결한 과정은 트러블슈팅 문서로, 새롭게 공부한 내용은 각각의 기술 개념 문서로 정리하고 싶었다. 그리고 이 문서들을 관련 프로젝트와 서로 연결하는 것이다.
이렇게 하면 같은 기록도 여러 관점에서 살펴볼 수 있다.

- 글 종류로 보기: 프로젝트, 트러블슈팅, 개념 문서처럼 글의 성격으로 모아 본다.
- 분야와 태그로 보기: 백엔드, 프론트엔드처럼 기술 분야나 태그를 기준으로 찾는다.
- 연결로 보기: 개념 문서에서 그 개념을 활용한 프로젝트와 문제 해결 기록까지 관계를 따라간다.

결국 글을 각각의 카테고리에 따로 쌓아 두는 것이 아니라, 하나의 기록을 여러 경로로 찾아보고 관련 지식으로 계속 이동할 수 있는 구조를 만들고 싶었다.

## mybr.ai — my digital brain, powered by ai.

사이트 이름은 **mybr.ai**로 정했다.

> *my digital brain, powered by ai.*

내가 공부하고 경험한 내용을 디지털 공간에 옮겨 놓은 또 하나의 뇌라는 콘셉트다.

크게 세 영역으로 나누었다.

- **Knowledge:** Backend, Frontend, AI 등 공부한 기술 개념과 원리
- **Experience:** 프로젝트, 트러블슈팅, 알고리즘 풀이, 회고
- **AI Hub:** AI 도구와 플러그인, Skills 활용 후기 및 개발 실험 기록

이 분류는 글을 찾기 위한 기준일 뿐이다. 실제로는 Knowledge에서 정리한 개념이 Experience의 프로젝트와 연결되고, AI Hub에서 다룬 기술이 다시 Knowledge 문서와 연결될 수 있다.

문서를 정리하는 정도에도 뇌와 관련된 이름을 붙였다.

| 상태 | 의미 |
|---|---|
| Impulse | 처음 발견하거나 기록한 지식 |
| Synapse | 다른 개념이나 경험과 연결하며 발전시키는 지식 |
| Engram | 충분히 이해하고 검토해 정리한 지식 |

실제 뇌의 공식적인 처리 단계를 나타내는 용어는 아니고, 사이트 콘셉트에 맞춰 정한 문서 관리 방식이다.
Engram이라고 해서 완성되어 더 이상 수정하지 않는다는 뜻도 아니다. 새로운 경험이 생기면 기존 문서를 수정하고 다른 개념과 다시 연결할 수 있다.

## 기술 스택 선정

처음부터 복잡한 웹 애플리케이션을 만들 생각은 없었다. 우선 글을 편하게 작성하고, 방문자가 읽기 좋고, 나중에 검색과 문서 연결 기능을 추가할 수 있는 구조가 필요했다.

기술을 선택하기 전에 다음과 같은 기준을 세웠다.

- Markdown 기반으로 글을 작성하고 관리할 수 있을 것
- 별도의 서버나 데이터베이스 없이 운영할 수 있을 것
- 나중에 Wikilink, 백링크, Knowledge Graph를 추가할 수 있을 것
- 문서가 빠르게 로딩되고 검색엔진에서도 잘 발견될 수 있을 것
- 가능한 한 무료로 운영할 수 있을 것
- Git을 이용해 글과 코드를 함께 관리하고 자동 배포할 수 있을 것

이 기준을 바탕으로 프레임워크는 Astro, 호스팅은 GitHub Pages를 선택했다.

### 프레임워크: Astro

처음에는 React로 개발하는 방법을 생각했다.
React는 익숙하고 인터랙션을 자유롭게 구현할 수 있다는 장점이 있다. 다만 mybr.ai에서 가장 중요한 기능은 복잡한 사용자 인터랙션보다는 **문서를 읽고, 찾고, 관련 지식으로 이동하는 경험**이다.

그래서 React, Next.js, Astro를 비교했다.

| 기술 | 장점 | 고려한 점 |
|---|---|---|
| React + Vite | 익숙한 환경, 높은 UI 자유도 | Markdown 기반 라우팅과 정적 페이지 생성 구조를 별도로 구성해야 함 |
| Next.js | 라우팅, 정적 생성, SSR 등 다양한 기능 제공 | 이번 프로젝트에는 필요하지 않은 기능까지 고려하게 될 수 있음 |
| Astro | Markdown 콘텐츠 관리, 정적 HTML 생성, 선택적인 JavaScript 사용 | 콘텐츠 중심 사이트라는 목적에 잘 맞음 |

Astro를 선택한 이유는 크게 세 가지다.

**첫째, Markdown 기반 콘텐츠 관리가 편리하다.**

Astro의 Content Collections를 사용하면 Markdown 문서의 메타데이터를 스키마로 검증하고, 해당 데이터를 이용해 글 목록과 상세 페이지를 생성할 수 있다.
mybr.ai에서는 글마다 고유 ID, 기술 분야, 글 유형, 문서 상태 등을 관리하려고 한다. 단순히 Markdown 파일을 화면에 보여주는 것에서 나아가 문서 데이터를 구조적으로 관리할 수 있다는 점이 마음에 들었다.

**둘째, 정적 사이트에 적합하다.**

Astro는 빌드 시점에 HTML을 생성할 수 있다. 페이지를 보여주기 위해 매번 서버에서 렌더링할 필요가 없고, 일반적인 문서 페이지에 불필요한 JavaScript를 전달하지 않아도 된다.
글을 읽는 경험이 중요한 사이트인 만큼 적합한 방식이라고 판단했다.

**셋째, 필요한 부분에만 인터랙션을 추가할 수 있다.**

문서 간 관계는 그래프로 시각화했고, 노드를 클릭하거나 확대·축소하면서 탐색할 수 있다.
Astro를 사용하면 일반 문서 페이지는 정적으로 유지하면서, 그래프처럼 동적인 기능에만 JavaScript를 적용할 수 있다.
처음부터 사이트 전체를 복잡한 웹 애플리케이션으로 만들 필요가 없다는 점이 좋았다.
결국 mybr.ai는 웹 애플리케이션이라기보다 **콘텐츠를 중심으로 구성되는 지식 시스템**에 가깝다. Astro가 그 목적에 가장 적합하다고 판단했다.

### 호스팅: GitHub Pages

Astro를 선택한 다음에는 배포 환경을 고민했다.

정적 사이트를 만들기로 했으니 서버를 직접 운영할 필요는 없었다. 무료로 운영할 수 있고, Git과 연동해 자동 배포할 수 있는 플랫폼이면 충분했다.

| 플랫폼 | 장점 | 고려한 점 |
|---|---|---|
| GitHub Pages | 무료 정적 호스팅, GitHub Actions 연동 | 정적 파일 중심이며 서버 기능은 제공하지 않음 |
| Vercel | 편리한 배포와 미리보기 기능 | 현재 필요한 범위보다 제공 기능이 넓음 |
| Cloudflare Pages | 정적 호스팅과 CDN 제공 | 좋은 대안이지만 초기 요구사항에서는 필수적인 차이가 크지 않음 |

최종적으로 GitHub Pages를 선택했다. Markdown 문서와 코드를 GitHub 저장소에서 함께 관리하고, 변경사항을 반영하면 GitHub Actions가 Astro 프로젝트를 빌드해 배포하도록 구성할 수 있기 때문이다.
개발 블로그와 Wiki는 글을 발행하고 끝내는 공간이 아니라 계속 수정하는 공간이다. Git으로 변경 이력을 남길 수 있다는 점도 잘 맞았다. AI를 이용한 콘텐츠 정리나 문서 관계 추천은 로컬 또는 별도 환경에서 수행하고, 검토한 결과만 정적 사이트에 반영할 계획이다.

따라서 지금 단계에서는 별도의 백엔드 없이 GitHub Pages만으로 충분하다고 판단했다.
물론 공개 저장소에 비공개 문서나 개인 정보, 회사 내부 자료가 포함되지 않도록 주의해야 한다. 공개용 콘텐츠는 별도로 선별하고 검수하기로 했다.

### 최종 기술 스택

| 영역 | 기술 | 선택 이유 |
|---|---|---|
| 프레임워크 | Astro | 콘텐츠 중심의 정적 사이트 |
| 언어 | TypeScript | 데이터 구조와 메타데이터의 타입 안정성 |
| 콘텐츠 | Markdown | 간편한 작성과 유지보수 |
| 데이터 검증 | Content Collections + Zod | 문서 스키마 검증 |
| 스타일링 | CSS + Astro Components | 불필요한 JavaScript 최소화 |
| 호스팅 | GitHub Pages | 무료 정적 사이트 운영 |
| CI/CD | GitHub Actions | Git 기반 자동 빌드 및 배포 |

전체 흐름은 다음과 같다.

```text
Markdown 콘텐츠
        ↓
Astro + Content Collections
        ↓
정적 HTML / CSS / JavaScript
        ↓
GitHub Actions
        ↓
GitHub Pages
```


**처음부터 모든 기능을 구현하기보다, 먼저 잘 읽히는 블로그를 만들고 점진적으로 Wiki 기능을 확장하기로 했다.**

## 왜 로컬 Wiki가 아니라 공개 사이트로 만드는가

이미 로컬에서 LLM Wiki를 구축하고 있었는데, 굳이 공개 사이트를 별도로 만드는 이유도 있다.

로컬 Wiki는 AI가 활용할 수 있도록 지식과 맥락을 구조화해 두는 공간에 가깝다. 반면 mybr.ai는 **사람이 읽고 이해하고 탐색할 수 있도록 정리한 지식 공간**으로 운영하려고 한다.

모든 로컬 문서를 그대로 공개하는 것은 아니다.

외부에 공유할 수 있는 기술 개념이나 경험을 선별하고, 필요한 경우 내용을 다시 정리해 공개할 생각이다.

또 하나의 목적은 **사이트를 만드는 과정 자체를 개발 경험으로 남기는 것**이다.

최근 AI 코딩 도구가 발전하면서 직접 코드를 작성하는 것 외에도, 요구사항을 정의하고 AI에게 작업을 맡기고 결과를 검증하는 방식이 중요해지고 있다고 느꼈다.

그래서 이번에는 단순히 사이트를 만드는 데서 끝내지 않고, 그 과정에서 사용한 AI 도구와 Skills, 프롬프트, 수정 과정까지 기록해 보고 싶었다.

## AI에게 맡길 일과 내가 직접 판단할 일

이번 프로젝트에서는 단순히 "개발 블로그를 만들어 줘"라고 요청하는 대신, 먼저 어떤 사이트를 만들고 싶은지 정리했다.

사이트의 목적, 콘텐츠 분류, 문서 데이터 구조, 디자인 방향, 배포 조건을 Markdown 문서로 작성했다. 이후 AI 코딩 도구가 이 문서를 참고해 작업하도록 구성했다. 작업별로 반복해서 적용할 수 있는 규칙은 Skills로 관리하는 방법도 검토했다.

예를 들어 디자인에서는 Hallmark, Frontend Design, Taste Skill 같은 도구를 공식 문서 기준으로 비교한 뒤 Hallmark를 사용했다. 단순히 화려한 화면을 만드는 것보다, 일관된 디자인과 긴 글의 가독성을 유지하는 것이 목표였기 때문이다.

문서 연결에서도 AI가 관련 개념을 추천하도록 만들 수 있겠지만, 최종적으로 의미 있는 관계인지 판단하는 것은 직접 해야 한다고 생각했다.

AI에게 맡길 수 있는 일과 직접 판단해야 할 일을 구분하는 것이 중요했다.

- AI는 구현 방법을 제안하고 반복적인 작업을 도울 수 있다.
- 실제 요구사항에 적합한지 판단하는 것은 개발자의 역할이다.
- 검증 가능한 기능은 테스트와 실행 결과로 확인한다.
- AI가 생성한 내용이라도 실제 경험이나 사실과 다르면 수정한다.


## 첫 번째 배포까지

첫 번째 목표는 모든 Wiki 기능을 완성하는 것이 아니었다. 우선 사이트를 실제로 공개하고, 첫 글을 읽을 수 있는 상태까지 만드는 것이었다.
그래서 작업을 단계별로 나눴다.

1. **디자인 방향 설정:** 디자인 스킬 Hallmark를 사용해 색상, 타이포그래피, 여백 등의 기준을 정하고 홈 화면을 구성했다.
2. **콘텐츠 데이터 모델 설계:** 문서의 ID, 분류, 상태 등을 표현하는 메타데이터 구조를 정의했다.
3. **글 읽기 화면 구현:** Markdown 콘텐츠를 웹페이지로 보여주고 Knowledge, Experience, AI Hub를 탐색할 수 있도록 구성했다.
4. **Neural Map 시각화:** 문서의 메타데이터를 기반으로 지식의 연결 관계를 그래프로 표현했다. 개별 글을 목록으로 보는 것뿐 아니라, 전체 문서가 어떻게 연결되어 있는지 시각적으로 탐색할 수 있도록 했다.
5. **품질 점검:** 반응형 레이아웃과 메타데이터, 문서 링크 등을 확인했다.
6. **배포:** GitHub Actions를 이용해 GitHub Pages에 사이트를 배포했다.

2026년 11월 8일, 첫 버전을 배포했다.

사이트를 보는 방법은 [소개 페이지](../../about)에 정리했다. 글을 읽거나 그래프에서 점을 누르면 그 자리가 '내가 지나간 길'로 남는다. 이 기록은 읽는 사람의 브라우저에만 저장되고 어디로도 보내지 않으며, 최근 40곳까지 남는다. 사이드바의 '내 길 지우기'로 언제든 지울 수 있다.

현재 화면과 콘텐츠 구조는 완성된 결과라기보다 앞으로 발전시킬 출발점에 가깝다. 특히 사이트의 핵심으로 생각하고 있는 문서 간 연결 기능은 계속 확장할 예정이다.

## 앞으로 할 것

기존 티스토리에 작성했던 글과 로컬 Wiki에 정리한 문서들도 하나씩 가져와 다시 정리하려고 한다.
단순히 글을 복사하는 것이 아니라 중복되는 설명은 공통 개념 문서로 분리하고, 프로젝트나 트러블슈팅 문서에서 해당 개념을 참조하도록 만들고 싶다.

AI Hub에는 사이트를 개발하며 사용한 플러그인과 Skills의 실제 사용 후기, 비교 결과, 자동화 실험도 기록할 예정이다.
[Astro를 처음 접하며 공부한 개념](../astro-basics)이나 GitHub Pages 배포 과정도 별도의 기술 글로 정리할 생각이다.

그렇게 경험과 지식이 하나씩 쌓이고 연결되면, mybr.ai도 처음 구상했던 디지털 두뇌의 모습에 조금씩 가까워질 것이다.
