[DevWiki 구축기](../../paths/path-devwiki-build/) 3편 — v2·v3 이관과 첫 운영

[2편](../devwiki-first-architecture)에서는 번호 폴더 Vault와 Project → Task → Session으로 구성한 v1을 살펴봤다. 이번 편은 그 구조를 9월 13일부터 15일까지 연달아 바꾼 이야기다. 이 사흘 사이에 v2와 v3로 두 번 바뀌었다.

```text
9/13   v2  Vault를 이관: 번호 폴더 → 소속만 폴더로
9/14   v2  에이전트 메모리를 Task 중심으로 정리
9/14   v3  "Session은 파일이 아니라 엔트리"로 기록 단위를 줄임 + 첫 스킬
9/15   v3  쓰자마자 나온 문제들 보완
```

변경한 이유는 대부분 사용하는 비용이 설계의 이득보다 컸기 때문이다. `Ruled Out`, 읽기 예산, 에이전트별 기록 분리 같은 원칙은 대부분 유지하면서 실행하는 형태를 바꿨다.

## v2: 폴더는 큰 소속만 표현한다

가장 먼저 번호 폴더 구조를 바꿨다. 프로젝트마다 `00-Project`부터 `99-History`까지 두는 v1은 문서의 성격과 위치를 폴더가 결정한다고 가정했고, 그 가정이 중복을 낳았기 때문이다. v1과 v2의 차이는 관계를 어디에 두는가에 있었다.

| 구분 | v1 | v2 |
|---|---|---|
| 폴더의 역할 | 성격과 관계까지 표현 | 큰 소속만 표현 |
| 관계 | 번호 폴더 계층 | WikiLink와 frontmatter |
| MOC | 허브 | 규칙의 진입점 |

관계 메타데이터에는 `project`, `task`, `related`, `sources`를 사용했다. 최상위 구성도 v1의 영역 번호 8개에서 `00-System`, `01-Inbox`, `10-Projects`, `20-Knowledge`, `30-Experiences`, `90-Archive`와 블로그로 정리했다.

HowTo는 별도 영역 대신 Knowledge의 `type: howto`로 합쳤다. 분류도 폴더보다 내용을 기준으로 판단했다.

- 프로젝트에 종속되면 `10-Projects`
- 재사용되는 지식이면 `20-Knowledge`
- 1인칭 경험이면 `30-Experiences`
- 불확실하면 Inbox에 검토 상태로 보관

### 이관 결정은 여섯 가지로 제한했다

문서가 수백 개여서 한 번에 옮길 수는 없었다. 문서마다 현재 경로, 제안 위치, 결정, 확신도, 근거, 사람 검토 필요 여부를 한 레코드에 적었다.

| 결정 | 의미 |
|---|---|
| `KEEP` | 그대로 유지 |
| `MOVE` | 새 위치로 이동 |
| `SPLIT` | 한 문서를 여러 개로 분리 |
| `MERGE` | 중복 문서를 하나로 통합 |
| `ARCHIVE` | 활성 목록에서 제외하고 보관 |
| `REVIEW` | 판단을 보류하고 사람이 검토 |

이동 전에는 파일명 중복과 링크 충돌을 확인했다. `git mv`로 이력을 보존하는 이동을 먼저 수행하고, 확신이 낮으면 `REVIEW`로 남겼다. 원본은 자동 삭제하지 않았고, 구 구조는 활성 자료에서 빼서 `90-Archive/Legacy`에 보존했다.

이관 전에는 스냅샷 커밋부터 남겼다. 되돌릴 수 있다는 확신이 있어야 판단도 빨라졌다. 9월 13일에는 스냅샷 → 결정적인 루트 이관 → 대체된 묶음 보관 → 승인된 Inbox 기록 이관 → 핵심 문서 v2화 순서로 커밋 몇 개를 만들었다. 이튿날에는 프로젝트 규칙과 템플릿을 새 구조에 맞췄다.

## 에이전트 메모리도 Task 중심으로 정리했다

Vault 구조는 정리됐지만 에이전트 메모리는 여전히 v1의 Session 파일 중심 설계였다. 9월 14일에는 이 부분도 다시 정리했다.

```text
Project = 저장소(repository) 하나의 컨테이너          ← v1과 달라진 정의
Task    = 의미 있는 개발 작업 하나
Session = Claude/Codex 한 번의 작업 맥락
```

Task마다 요구사항·결정·구현 문서를 둘 하위 폴더가 생겼다.

```text
10-Projects/<Project>/
├── project.md              저장소의 안정적인 정체성과 목차
├── state.md                프로젝트 수준 짧은 스냅샷
└── Tasks/<task-id>/
    ├── task.md             목표·범위·현재 상태·다음 행동
    ├── Requirements/       이 작업에만 해당하는 요구사항
    ├── Decisions/          선택지·제약·근거·결과
    ├── Docs/               현재 구현 구조 (코드 복사 대신 저장소 참조)
    └── Sessions/           세션 한 번의 작업 기억과 인계
```

코드는 저장소에, 이유는 기억에 둔다는 원칙을 유지하면서 문서의 자리를 늘린 것이다. 공유 스킬의 생명주기는 `project`, `task`, `resume`, `sync`의 네 가지로 정했다.

### 실제 Task 두 개에 적용하자

| 관찰 | 드러난 문제 |
|---|---|
| 템플릿에 Requirements가 2개, Tried·Findings·Decisions·Next도 각각 2개 | 같은 내용을 어디에 쓸지 에이전트가 매번 판단 |
| 한 Task의 `task.md`가 223줄 | Decisions의 옵션 비교와 Docs의 구현 지도가 전부 `task.md`로 들어감. 작업 로그가 아니라는 규칙이 지켜지지 않음 |
| 다른 Task의 67줄 중 상당수가 “없음”, “미확인”, `not recorded yet` | 추측 금지 원칙이 무지의 기록을 양산 |
| 저장소 1개가 Project 2개에 매핑되고, Project 2개는 저장소가 없음 | 경로만으로 Project를 결정하지 못해 공유 저장소에서는 매번 되물어야 함 |
| 같은 규칙이 `CLAUDE.md`, `AGENTS.md`, 기록 규칙, 탐색 전략, 스킬 파일의 5곳에 분산 | 규칙이 이미 서로 어긋남 |
| 실제 Session 파일 0개, 지식 승격 0건 | 기록 비용이 사용을 막는 문턱이 됨 |

2편에서 걱정한 규칙 분산과 파일 단위 기록 비용이 그대로 나타났다.

> 문제는 원칙이 아니라 원칙의 충실도를 문서 개수와 섹션 개수로 표현한 것이었다.

Task ≠ branch ≠ session, 코드는 Repo에 맥락은 Wiki에, Git이 Source of Truth라는 원칙은 유지했다. 같은 원칙을 더 낮은 기록 비용으로 실행하는 것이 v3의 목표였다.

## v3: Session은 파일이 아니라 엔트리다

같은 날 오후 설계를 다시 썼다. 핵심 결정은 여덟 개였다.

| 결정 | 선택 | 근거 |
|---|---|---|
| D1 | Project는 일의 맥락. 저장소와 N:M 관계 | 실제 설정이 이미 N:M. 1:1을 강제하면 저장소 없는 Project를 담을 수 없음 |
| D2 | Task 내부는 `task.md`, `decisions.md`, `sessions.md`의 3파일. 필요할 때만 폴더로 확장 | 폴더·번호·12개 섹션 템플릿이 결정 하나를 남기는 비용을 높임 |
| D3 | Task는 에픽 단위. 단발 작업은 Project의 `log.md` 한 줄 | 주 단위 Task는 연 50개 폴더를 만들고 결정도 50곳에 분산 |
| D4 | identity는 저장소의 `.devwiki` 포인터 | 공유 저장소의 모호함을 없애고 worktree별로 다른 Task 선택 가능 |
| D5 | `state.md`를 폐지하고 `project.md`로 통합 | 7개 중 5개가 빈 껍데기 |
| D6 | 기존 Project 수준 ADR 11개는 현 위치 보존 | 이동 시 링크가 깨지고 얻는 이점이 없음 |
| D7 | 기록 자동화 훅 제외 | [훅 검토 과정](#훅은-일단-만들지-않기로-했다)에서 설명 |
| D8 | Knowledge 승격 경로 제외 | 매 세션 승격 여부를 판단하는 비용이 기록 비용보다 컸고, 승격은 0건 |

작업 단위도 다시 정의했다.

| 단위 | 정의 | 판별 기준 |
|---|---|---|
| Project | 끝이 없는 일의 맥락 | “이거 끝났어?”에 답할 수 없으면 Project |
| Task | 끝났다고 말할 수 있는 에픽 | 보통 2주~2개월, 여러 PR |
| Workstream | Task 안의 갈래 | branch·worktree·PR이 연결되는 자리 |
| Session | 에이전트가 한 번 일한 것 | 파일 대신 `sessions.md`의 엔트리 |

```text
10-Projects/<Project>/
├── project.md        안정 정보 + 짧은 현재 상태
├── log.md            Task를 만들지 않는 단발 작업, 한 줄씩
└── Tasks/<task-id>/
    ├── task.md       30줄 상한
    ├── decisions.md  최신이 위, 5필드 고정
    └── sessions.md   최신이 위, 엔트리당 15줄 상한
```

`Decisions/`, `Docs/`, `Requirements/`는 처음부터 만들지 않았다. 결정이 15개를 넘거나, 같은 구조 설명을 두 번 찾게 되거나, 요구사항이 `task.md`를 넘칠 때만 만들었다. 빈 폴더와 빈 섹션이 쌓인 v2에 대한 대응이었다.

### 기록 양식과 현재 상태를 줄였다

`decisions.md`는 옛 ADR의 12개 섹션을 다섯 필드로 줄였다.

```markdown
## 날짜 · 결정 제목
- **맥락**: …
- **선택**: …
- **버린 것**: …
- **근거**: …
- **재검토**: …
```

“버린 것”은 왜 쓰지 않기로 했는지, “재검토”는 조건이 변했는지를 확인하는 칸이었다. [1편에서 다룬 폐기한 방법의 재제안](../devwiki-why#ai가-이미-폐기한-방법을-또-제안한다)과 [결정 이유의 망각](../devwiki-why#우리-이거-왜-이렇게-했더라)에 대응했다.

Session은 v1의 여섯 칸을 다음 엔트리로 줄였다.

```markdown
## 2026-09-14 14:30 · claude · 작업 제목
- 브랜치 · 커밋 범위
- 한 것: …
- 안 된 것: … ← 이미 시도해서 안 된 것. 다시 시도하지 말 것
- 확인: …
- 다음: …
```

“안 된 것”은 v1의 `Ruled Out`을 압축한 칸이다. 양식은 줄였지만 이미 폐기한 방법을 다시 제안하지 않게 하는 목적은 유지했다.

내용이 있는 섹션만 쓰고 “없음”은 적지 않기로 했다. v2에서는 없음·미확인이 무지의 기록을 양산했기 때문이다. 모르는 내용은 `(추정, 미검증)`으로 표기했다.

`task.md`에서는 브랜치·커밋의 Git 스냅샷을 뺐다. Git이 정본인데 문서로 복사하면 낡기 때문에 시작할 때 실제 Git을 읽게 했다. Execution Contexts는 Workstreams와 중복돼 삭제했고, Tried·Failed·Verified·Blockers 같은 세션 단위 사실은 `sessions.md`로 옮겼다.

### Project와 Task는 .devwiki로 지정한다

저장소 루트에는 다음 두 줄을 뒀다.

```yaml
project: <프로젝트>
task: <task-id>
```

개인 설정이므로 저장소에 커밋하지 않도록 `.gitignore` 대신 `.git/info/exclude`에 등록했다. worktree마다 독립적인 포인터를 두어 서로 다른 Task를 가리킬 수 있게 했다. `config.yaml`은 Project에서 저장소를 찾는 역방향 조회용으로만 남겼다.

## 훅은 일단 만들지 않기로 했다

기록이 사람의 의지에 달린 것이 v2 실패의 첫 원인이라고 봤다. 그래서 세션 종료와 압축 시점의 자동 기록 훅을 검토했지만, 당시 결론은 만들지 않는 것이었다.

아래는 그때 확인한 훅의 동작과 판단이다.

| 훅 | 당시 확인한 내용 |
|---|---|
| `PreCompact` | `additionalContext` 주입 미지원. 처음에는 지원한다고 잘못 판단했고, 사용자가 그 전제로 선택한 뒤 검증해 철회 |
| `Stop` / `UserPromptSubmit` | 주입은 가능하지만 매 턴 발동해 기록 노이즈가 큼 |
| `SessionEnd` | 차단과 주입 모두 불가 |

더 근본적인 이유도 있었다.

> 자동 기록은 "무엇을 남길지" 판단을 기계에 맡기는 것인데, v2에서 문제였던 건 분량이 아니라 판단이었다. 측정 없이 자동화를 얹으면 쓰레기를 더 빨리 쌓는다.

기록은 `/dev-memory save`를 직접 호출할 때만 남기기로 했다. 2주 뒤 스킬 실행 후 사람이 설명을 덧붙였는지 세어 훅을 다시 검토할 계획이었다. 이 결정은 일주일 만에 뒤집혔다. 그 과정은 [4편](../../topics/plan-devwiki-hooks)에서 다룰 예정이다.

## 첫 dev-memory 스킬

v1의 `memory-start`, `memory-checkpoint`, `memory-wrap`은 구현하지 못했다. 실제 첫 스킬은 v3를 만든 9월 14일 `dev-memory`라는 이름으로 나왔다. 스킬을 쓰는 기본 방식은 이후에도 크게 바뀌지 않았다.

### 개념은 정본에, 절차는 스킬에

같은 규칙이 다섯 문서에 흩어져 어긋나기 시작했으므로 역할을 분리했다.

| 문서 | 역할 |
|---|---|
| `Agent-Memory-Rules` | 규칙과 개념의 정본 |
| 스킬 파일 | 절차만 작성. 개념 설명은 정본으로 연결 |
| `CLAUDE.md`, `AGENTS.md` | 포인터만 유지 |

| 명령 | 역할 |
|---|---|
| `start` | 읽기 예산을 파일 4회로 고정해 작업 이어받기 |
| `save` | 세션 끝에 현재 상태 기록 |
| `task` | 새 Task 생성 |

`start`는 `.devwiki`, Task 문서, 가장 최근 Session 하나, 실제 Git 상태만 확인했다. v1의 읽기 예산을 파일 네 번이라는 수치로 구체화한 것이다. Git과 문서가 다르면 Git을 현재 사실로 삼고 차이를 기록했다.

`save`의 첫 시험에서는 하지 않은 작업이 기록될 뻔했다. 그날은 Vault에서만 작업했는데 스킬을 그대로 실행하면 다른 작업 기록을 남기는 상황이었다. 그래서 한 일이 없으면 기록하지 않는 가드를 추가했다.

- Project 정체성(identity)은 추측하지 않는다. 어느 Project의 작업인지 모호하면 한 번 묻는다.
- 내용은 추측하되 `(추정, 미검증)`으로 표기한다. 모르는 것을 빈칸으로 두지 않는다.
- Git을 현재 구현의 정본으로 삼는다.
- 사용자가 바꾼 파일, 비밀 후보 파일, `.git`, 바이너리는 열거나 수정하지 않는다.
- 같은 Session 엔트리는 한 에이전트만 쓴다.

### 실패하는 게이트부터 만들었다

문서와 스킬 작업에는 단위 테스트가 없었다. 대신 폐지된 구조를 가리키는 참조 0건, 정본 문서의 새 스키마 포함, 깨진 링크 없음 같은 불변식을 확인하는 셸 게이트를 먼저 만들었다.

1. 검사를 먼저 쓰고 일부러 실패시킨다.
2. 작업을 하나씩 끝내며 검사 항목을 통과시킨다.
3. 작업 중 발견한 구멍을 검사에 추가한다.

처음 9개였던 검사는 이후 12개로 늘었다. 구현 계획서에는 단계별 실행을 위한 `subagent-driven-development` / `executing-plans` 스킬도 명시했다.

운영 중에는 다음 문제도 남았다.

- 스킬이 Vault 밖의 사용자 설정 디렉터리에 있어 Git 추적을 받지 못했다. 수정 전 백업이 필요했고, 나중에 정본을 Vault로 옮기는 이유가 됐다.
- 존재하지 않는 `/dm`을 문서에 적었다가 실제 이름 `/dev-memory`로 일괄 정정했다. 호출명은 만든 직후 먼저 검증해야 한다고 생각했다.
- 몇 번의 개편으로 스킬 파일이 약 32KB까지 커졌다. 10월 말 절차와 필요할 때 읽는 참고 문서를 분리해 약 13KB로 줄였다. 이 과정은 [7편](../../topics/plan-devwiki-skill-evolution)에서 다룰 예정이다.

스킬을 쓴 뒤 2주 동안은 다음 질문을 기준으로 삼았다.

> start 후에 내가 손으로 프로젝트 설명을 추가했는가?

그렇다면 구조가 실패했다고 봤다. Task 크기와 기록량, 번거로운 지점이 이 지표에서 드러날 것이라고 생각했다.

## 같은 날 이관까지 실행했다

설계가 끝난 뒤 구현 계획을 8개 작업으로 나눠 에이전트가 하나씩 실행했다.

- `state.md` 7개를 각 `project.md`의 `## 현재`로 접고 삭제했다.
- 223줄이던 `task.md`를 v3의 `task.md` 30줄과 `decisions.md`로 분해했다.
- 67줄 중 대부분이 미확인이던 Task는 버리고 그 이유와 발견을 기록했다.
- 빈 v1 폴더 10개를 삭제하고 내용이 남은 폴더에는 색인을 붙였다.
- 활성 저장소 4곳에 `.devwiki`를 만들고 `.git/info/exclude`에 등록했다.

게이트의 9개 검사는 모두 통과했다. 하지만 점 폴더를 스캔하지 않는 것, 재생성 가능한 캐시 폴더, 상대 경로 위키링크 `[[../../state]]`를 잡지 못하는 구멍을 발견해 보완했다.

첫 dry-run에서는 파일 3개와 Git을 읽었고, 질문 0회, 사람이 덧붙인 설명 0건이었다. 이 수치를 바로 성공으로 해석하지는 않았다.

> 읽은 파일 수는 예산 안이지만, 그 task.md가 228줄이라 읽기량은 30줄 상한의 의도를 한참 넘겼다. 읽기 예산을 파일 수로만 재는 것의 한계이며, 재작성 전까지 이 수치를 성공으로 읽지 않는다.

측정을 통과한 숫자와 함께 측정의 한계도 남겼다.

## 쓰자마자 드러난 문제를 고쳤다

v3 첫날에는 규칙을 쓴 세션에서 바로 규칙을 어기는 일이 나왔다.

### Task가 끝난 뒤의 결정은 어디에 남기는가

첫 실제 `save`에서는 Task 종료 후 내린 구조 결정이 갈 곳을 찾지 못했다. `decisions.md`가 Task 안에만 있었기 때문이다. `log.md` 한 줄로 줄이면 버린 것과 재검토 조건이 사라졌다.

Project 루트에도 `decisions.md`를 항상 두고, `Docs/`와 `Requirements/`도 Task와 같은 조건으로 확장할 수 있게 했다. 구분 기준은 수명이었다.

> Task가 끝나도 계속 참이면 Project 수준이다. 기준은 수명이다.

파일 하나를 늘리는 비용도 기록했다.

> 파일을 하나 늘리는 대신 판단 기준을 수명 하나로 고정했다. 2주 뒤 이 파일이 비어 있으면 과잉 구조였다는 뜻이다.

### 위키링크가 실제로 연결되지 않았다

v3 문서 8개가 `[[Docs/x]]`나 `[[../task]]` 같은 링크를 사용했다. 당시 확인한 Obsidian의 위키링크 해석에서는 `../`를 사용할 수 없었고, `[[Docs/x]]`는 Vault 루트를 기준으로 해석됐다. 링크가 아무 데도 가지 않았고, 클릭하자 Vault 루트에 빈 `Docs/`가 생겼다.

- 문서 이름이 유일하면 `[[이름]]`을 쓴다.
- `task`, `decisions`, `log`, `project`처럼 겹치는 이름은 Vault 루트부터 전체 경로를 쓴다.

`10-Projects/`의 링크를 전수 검사하자 깨진 링크가 28건이었다. 대부분 v1 때부터 남아 있었다. 게이트가 폐지된 구조만 검사하고 실제 링크는 보지 않았기 때문이다. 링크 검사를 게이트의 10번 항목으로 추가했다.

> 사람이 링크 형식을 지키는 것에 의존하는 안은 버렸다. 규칙을 쓴 그 세션 안에서 실패가 증명됐기 때문이다.

### 한글 정규화 때문에 존재하는 문서도 없다고 나왔다

링크 검사가 존재하는 문서를 깨진 링크로 판단했다. macOS 파일시스템의 한글 파일명은 NFD, Markdown 본문은 NFC로 저장돼 같은 글자가 다른 바이트로 비교된 것이 원인이었다. 아카이브에 원본이 있어도 문서가 없다고 오판할 뻔했다.

파일명과 링크 대상을 모두 NFC로 정규화한 뒤 비교하도록 고쳤다. 한글 파일명이 많고 iCloud·Obsidian·Git 사이에서 정규화가 달라질 수 있었으므로, 비교하는 시점에 맞추기로 했다.

### 과거 기록을 고쳐서 검사를 통과시키지는 않는다

게이트는 “state.md 7개를 접었다”는 Session 기록까지 폐지된 구조 참조로 판단했다. 폐지된 구조를 사용하는 문서와, 폐지했다고 기록한 문서를 구분하지 못한 것이다.

기록을 고쳐 통과시킬지, 이런 기록을 검사 대상에서 제외할지 선택해야 했다.

> append-only 기록은 과거에 한 일을 남긴 것이다. 검사기를 만족시키려고 고치는 순간 기록을 위조하게 된다.

`sessions.md`, `decisions.md`, `log.md`는 파일명 기준으로 해당 구조 검사에서 제외했다. frontmatter에 예외를 적는 방식은 어느 문서나 스스로 면제할 수 있어 검사를 무력화한다고 보고 사용하지 않았다.

## 규칙을 지키는 비용과 검증의 자리

| 변경 | 다룬 층 | 이유 |
|---|---|---|
| v1 → v2의 Vault 이관 | Vault 구조 | 폴더가 관계까지 표현하려다 중복 발생 |
| v2 → v3 | 기록 단위 | 파일 단위 기록의 판단·작성 비용이 사용을 막음 |
| v3 첫 운영 보완 | 검증 | 규칙을 쓴 세션에서도 어겨져 검사를 도구로 이동 |

규칙을 문서에 적는 것만으로는 지켜지지 않았다. 이 기간에는 규칙을 사람이 지키기 쉬운 형태와 도구가 검사하는 형태로 바꿨다. 이 방향은 이후 훅과 CLI로 이어진다.
